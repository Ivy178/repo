
# kafka是什么
Kafka 是一个分布式的消息队列和流处理平台，核心是发布订阅模型。
作用是解耦、削峰、异步和缓冲，让生产者和消费者互不依赖。
用途上，常做日志收集、消息系统、数据管道和实时流处理，比如埋点、订单、监控数据都走 Kafka。


# kafka架构
Producer 发消息到 Topic，Topic 分成多个 Partition，分区内有序，分区间并行；
每个 Partition 有 Leader 和 Follower 副本，Leader 读写，Follower 同步，副本保证高可用；
Consumer Group 并行消费，一个分区同一时刻只被组内一个消费者消费；
控制面用 KRaft 管元数据、选主和 Broker 上下线。

# kafka跟rabbitmq区别
Kafka 重吞吐、能回放；
RabbitMQ 重投递、重路由。

# rabbitmq跟redis区别
Redis 是缓存为主，顺带能排队；RabbitMQ 是专业邮局，专门可靠送消息。
简单异步、丢了无所谓，用 Redis；订单、支付、任务这种要可靠的，用 RabbitMQ。


# 性能调优
高吞吐：调大batch.size 和 linger.ms，压缩算法使用 lz4 或 zstd，适合日志收集类场景
低延迟：linger.ms 设置为 0，acks 设置为 1，实时监控告警
高可靠：acks=all 和 min.insync.replicas 至少是2，金融支付等场景
Consumer: 调大fetch.min.bytes 和 fetch.max.wait.ms,  提高吞吐量

> Rebalance 就是消费者组重新分活儿：有消费者加入、退出或分区数变了，Kafka 就把分区收回来重新分配。分配期间大家暂停消费，没提交 offset 的消息可能被重复消费，所以消费端要做幂等。
> ！Lag 就是消费者还欠着多少条消息没消费。


# 怎么处理积压
消息积压会打满磁盘、拖慢生产端，甚至雪崩。解决分三种情况：
消费能力不足，就加分区、加消费者，消费者数对齐分区数，别让消费者空转；
消费者够但处理慢，说明代码逻辑重，用多线程异步处理，但要注意自己保证顺序性；
下游处理不及时，就增大每批拉取量，比如从 500 调到 1000。核心原则就一条：让消费速度大于生产速度，积压自然就消了。   


# 如何防止丢失/重复
Kafka 默认是至少一次，所以既可能丢，也可能重。要防住，得从生产、Broker、消费三层下手。
防丢：
- 生产端设 acks=all，开重试和幂等；
- Broker 端副本设 3，设置min.insync.replicas=2 配合 acks=all，确保至少两个副本同步成功才确认写入，禁止 unclean 选举，不让掉队的副本当leader,防止丢数据；
- 消费端关掉自动提交，处理完再手动提交 offset。   

防重：
- 生产端开幂等，必要时用事务；
- 消费端必须做业务幂等，比如用唯一 ID 查 Redis 或数据库，处理过就跳过。

// 事务：中间失败就回滚，防止 offset 没提交，重启又消费一遍，


# 如何管理topic分区
Kafka 分区管理就两件事：策略选对、数量规划好。
策略上，有 key 就按 hash(key) % 分区数 路由，保证同 key 顺序；没 key 就轮询，负载更均匀。
数量上，分区太少并行度不够，太多元数据和 Rebalance 开销大。经验是分区数对齐消费者数、留扩展余量，单 Broker 控制在 2000 到 4000 以内。


>> 为什么分区只增不减
因为消息是按 key 哈希到分区的，分区数一变，哈希映射就变了。同一个 key 的消息可能被分到不同分区，顺序保证直接失效。
比如
    订单 1001 有三条消息：创建、支付、发货。
    它们 key 都是 1001，哈希后都进同一个分区，按顺序存。消费者也按顺序处理，不会先发货后支付。
    订单 1002 是另一个 key，可能进另一个分区，和 1001 并行处理，互不影响。
    如果不带 key，这三条消息可能轮询到不同分区，顺序就乱了，可能先处理发货再处理支付。

>> 消息去哪个分区分区
key 的哈希值 % 分区数

>> 分区扩多少
分区扩多少，核心看目标吞吐量。
用目标吞吐除以单分区实测吞吐，算出最少要几个；再向上取整到消费者线程数和 Broker 数的整数倍，留 20% 到 50% 缓冲。
同时记住上限：单 Topic 别超 100，单 Broker 别超 4000。
因为分区只能增不能减，带 key 扩容还会乱序，所以宁可提前多规划，上线后看 Lag 再微调。


>> 什么情况下扩Broker
出现这几种情况就该扩 Broker：磁盘快满了、CPU 或网络持续打高、单 Broker 吞吐到瓶颈、分区副本数接近上限，或者整体吞吐上不去。
扩完不会自动均衡，得用 kafka-reassign-partitions 把分区迁到新节点。
一句话：资源扛不住、容量不够、并行度上不去，就扩 Broker，扩完手动迁数据。

# 告警指标
需要重点监控以下指标：
· UnderReplicatedPartitions (URP)：副本未同步的分区数，正常应为 0，持续大于 0 意味着有 Broker 压力过大或网络故障。
· Consumer Lag：消费者积压量，直接反映消费是否跟得上生产，是重中之重。
· ActiveControllerCount：整个集群必须恒为 1，若出现 0 或大于 1，说明集群状态异常。
· 磁盘与资源：监控磁盘使用率、CPU、网络等。  // 过大可能需要扩broker


# 其他
> Kafka topics 和 partitions 的区别
Topic 是逻辑分类，比如订单一个 Topic、日志一个 Topic。
Partition 是 Topic 的物理分片，一个 Topic 可以分成多个 Partition。
消息实际存在 Partition 里，分区内有序，分区间并行。
所以 Topic 是“叫什么”，Partition 是“存哪里、怎么并行”。没有 Partition，Topic 就没法扩展和并行消费。


> at-least-once vs exactly-once 语义
At-least-once：至少一次，消息不丢，但可能重复。比如消费完还没提交 offset 就挂了，重启会再消费一遍。
Exactly-once：精确一次，不丢也不重。Kafka 靠幂等生产者和事务实现，但跨数据库、发短信这些外部系统，还得业务幂等兜底。
实际生产常用至少一次 + 消费端去重，来近似精确一次。

> 实际生产常用至少一次 + 消费端去重，来近似精确一次。
比如消费者扣完100,消费者崩了，没提交offset,重启后又扣100元
为了避免，消费端加去重：每条消息带唯一订单号。扣款前先查 Redis 或数据库，看这个订单号处理过没。处理过就直接跳过，不再扣款；没处理过才扣款，并记录订单号已处理。
这样，即使消息重复消费，业务也只执行一次。不丢靠 Kafka 的至少一次，不重靠消费端自己兜底，合起来就是业务上的精确一次。

> Rebalance是什么，有什么影响
- Rebalance 就是消费者组里重新分配谁消费哪些分区。触发原因一般是消费者上下线、分区数变化，或者处理超时被踢出组。
- 影响很大：期间全组暂停消费，可能重复消费，积压更严重。频繁 Rebalance 基本就是灾难，消费根本起不来。
- 所以对策是：调大超时参数、用粘性分配策略、保证 poll 循环别断。

> Poison message是什么
Poison message 就是“毒药消息”，指消费者怎么处理都失败的消息，比如格式错、数据缺、反序列化不了。
会让消费者反复重试、卡住，甚至阻塞整个分区，导致积压。
处理方式一般是限制重试次数，失败后扔进死信队列，再人工排查。


> 如何处理 poison messages
处理毒药消息，核心就一句：别让它卡住整个分区，隔离到死信队列。
具体分三步：
1. 捕获异常：消费端用 try-catch 包住处理逻辑，遇到反序列化失败或业务异常，别让消费者直接挂掉。
2. 限制重试：重试几次还失败，就别再重试了，否则会无限循环、阻塞分区。
3. 扔进死信队列：把坏消息发到另一个专门的 DLQ Topic，记录原始内容和错误原因，后续人工排查。同时加日志和告警，方便发现。
